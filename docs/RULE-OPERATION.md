# ルールの運用手順

`docs/RULES.md`(80件の索引)を**いつ・どれだけ見るか**と、
**ルールが無理だと分かったときにどうするか**を決めたもの。

## 設計方針

**「毎回全部読む」は必ず形骸化するので採らない。** 80件を毎回読む手順を作れば、
数回で読まなくなり、読んだことにして進む。今日(2026-08-12)起きたのがまさにそれで、
守れなかった2件はどちらもマニュアルに書いてあった。

代わりに3つに分ける。

| 層 | 何を | いつ | コスト |
|---|---|---|---|
| 1. 機械が見る | データの不変条件 | コミット前(自動) | ゼロ |
| 2. その場で読む | これからやる作業に関係する節だけ | 作業の種類が変わったとき | 1〜2分 |
| 3. 人が見る | 機械化できないもの | ユーザーが気づいたとき | — |

**層1を厚くして層2・3を薄くするのが目標。** 層2は人間(エージェント)の記憶に頼るので、
薄いほど守られる。

---

## 層1: 機械が見る(コミット前・自動)

フックの**正本は`tools/hooks/`**(git管理下)。`.git/hooks/`はその複製で、
**一致しているかを毎回確認している**(`tools/install_hooks.py --check`)。
`.git/hooks/`はgitの外なので、消しても書き換えても履歴に残らない。だから外から見る。

```bash
python tools/install_hooks.py           # 新しいクローン/worktreeで最初に1回
python tools/install_hooks.py --check   # 入っているか、正本と同じかを見る
```

| フック | いつ走るか | なぜ要るか |
|---|---|---|
| `pre-commit` | 普通のコミット | 本体 |
| `pre-merge-commit` | マージが作るコミット | マージでは`pre-commit`が呼ばれない |
| `pre-push` | push する直前 | rebase・cherry-pick・`--no-verify`は上2つを素通りする。**押し出す中身そのものを検査する** |

**手で起動しない。** 止まる条件:

1. 導入済みフックが正本と違う
2. 監査(`tools/audit_characters.py`)の**HIGHがベースラインより増えた**
3. **`approved:true` が新しく増えた**(D-14)
4. ステージしたページの**JSが構文エラー**(T-06/T-07)
5. **ルール文書の変更と作業の変更が同じコミットに混ざっている**(W-13)
6. `attack-simulator.html`を変えたのに`SIMULATOR_VERSION`を上げていない(P-03)
7. ステージ済みの内容と作業ツリーが食い違っている(検査した物とコミットする物が別になる)

警告だけ出る条件:

8. データを触っているのに `busho/` `skill/` `sitemap.xml` や prerender 対象に差分が無い(P-01/P-02)
9. 索引(`docs/RULES.md`)だけを変更している(W-14。原文も直したか)

```bash
python tools/precommit_check.py --accept --reason "なぜ残すのか"   # ベースラインに載せる
```

- ベースラインは `tools/audit_baseline.json`。既知の未解決分を置いて**「増えていないこと」だけ**を見る。
  全部ゼロにしてから運用開始、では永久に始まらないため。
- **意図的に残す場合も`--accept`で明示的にベースラインへ載せる。黙って通さない。**
- `git commit --no-verify` で迂回できてしまうが、**使ったら必ず報告する。**
- 完了報告には「私が確認した」ではなく**この出力を貼る**。
- チェックが存在しない項目について「問題ありません」と書かない。
  **「そのチェックは無い」と書く。**

### 「未確認」の証拠(I-01)

「未確認」と表示される段には、**どこを見たかの記録が2件以上**必要。
記録が足りなければ監査がHIGHを出す。

```bash
python tools/reslog.py                       # 何を調べたかの一覧
python tools/reslog.py --show TR:白銀双鶴     # 個別に見る
```

記録は `tools/research_log.json`(リポジトリ内なので消えない)。
調査スクリプトから `reslog.log(key, source, url, result, found)` で追記する。
**手で書き足して通すのは、口約束に戻るのと同じなのでしない。**

### チェックを足すときの義務

**新しいチェックを書いたら、直す前の状態で走らせて「何件検出できたか」を実出力で示す。**
2026-08-12の違反(S-01)は、自分で書いた検査がルールより狭いまま自分で合格判定したのが原因。
検出件数を出さないチェックは、動いている証拠が無いのと同じ。

コミットメッセージに件数を書く(例: 「リンク切れ203件を検出することを確認」)。

## 層2: その場で読む(作業の種類が変わったとき)

**作業を始める前に、下の表から該当行の節だけ`Read`する。** 記憶で済ませない。
同じ種類の作業を連続でやっている間は読み直さなくてよい(種類が変わったら読む)。

| これからやること | RULES.mdで読む節 | 終わったら実行 |
|---|---|---|
| 武将を新規登録する | 1・2・3・5 | `prerender` + `gen_detail_pages` + `check_js` + 監査 |
| 武将を青丸→黄丸にする | 1・2・3・4・5 + manual A-5の報告テンプレ | 監査 |
| **武将を黄丸→赤丸にする** | **やらない。** D-14によりユーザーが明言したときだけ。自分の判断で付けない | — |
| スキルページを作る/直す | 2・3・4 | `prerender` + `gen_detail_pages` + `check_js` + 監査 |
| 一覧ページを触る | 2・4 | `prerender` + `check_js` + 監査 |
| シミュレーターを触る | 6(P-03のバージョン) | 監査 |
| 表示・見た目を変える | 7 | 該当ページの目視 + 監査 |
| 記事を書く | 7(V-05/V-06) | — |
| スクリプトを書く | 9(環境の罠) | — |
| **worktreeをマージする** | 2(対の関係)・8 | マージ後に`prerender` + `gen_detail_pages` + 監査。**マージコミットも`pre-merge-commit`で検査される** |
| **監査の指摘をまとめて潰す** | 指摘の種別に対応する節 | 種別ごとにコミットを分ける。**一括置換のあとは必ず`check_js`** |
| **ルール文書を直す** | 下の「ルールが無理だと分かったときの手順」 | **作業と同じコミットにしない**(W-13。pre-commitが止める)。`python tools/rules.py` |
| **監査にチェックを足す** | 上の「チェックを足すときの義務」 | `audit_selftest.py`に注入ケースを追加し、検出できることを出力で示す |

**節を読むのは「作業の直前」であって、セッションの最初ではない。**
セッション冒頭にまとめて読んでも、3時間後には効かない。

**この表に無い作業を始めるときは、まず行を足す。**
「表に無いから読まなくてよい」という抜け道を残さないため。

## 層3: 人が見る

`RULES.md`で「機械×」のもの(進め方・報告・調査のしかた)。
これらは**エージェントが守る保証が無い**。ユーザーが違和感に気づいたときに指摘してもらう前提で、
指摘されたら層1に落とせないかをまず考える。

## ルールが無理だと分かったときの手順

**勝手に書き換えない。勝手に例外を作らない。黙って飛ばさない。**
今日、鍛錬表の表示規則とcategoryLinksの方針を作業の途中で自己判断で決めた(W-13)。

1. **作業を止める。** その場で回避策を実装しない。
2. **次の4点を書いて報告する。**
   - どのルール(ID)が
   - どういう状況で守れないのか(具体例つき)
   - 守ろうとするとどうなるか(所要時間・副作用)
   - 代案(あれば)
3. **承認を待つ。** 承認が無い間は、そのルールに関わる部分を未完了のまま残す。
   「とりあえず進めて後で直す」はしない。
4. **承認されたら、索引と原文の両方を直す。**
   `RULES.md`だけ直すと原文と食い違い、次に原文を読んだ人が古いルールに従う。
5. **変更の記録を残す。** 日付・理由・誰が承認したかをコミットメッセージに書く。

### 例外: 明らかな誤記・リンク切れ

原文の誤字、壊れたパス、既に存在しないファイルへの参照は、報告して直してよい。
**意味が変わる変更はすべて上の手順に乗せる。**

---

## ルールを破ってしまったときの手順

1. **気づいた時点で申告する。** 完了報告に混ぜて薄めない。
2. **何件影響したかを数える。** 「たぶん少ない」ではなく実データで数える。
3. **同じ違反が他にもないか横断で調べる。** 1件見つかったら必ず他も疑う
   (今日: 朝曇ノ明麗の`ownHiddenCandidate`1件から全222スキルを照合し、他に3件出た)。
4. **層1に落とせるかを考える。** 落とせるなら、直すのと同じコミットでチェックを足す。
5. **下のペナルティを適用する。**

## ペナルティ

### 前提: これは罰ではなく「信頼の巻き戻し」

エージェントに罰は効かない。損をした感覚が残らないし、セッションをまたぐと消える。
**効くのは「壊れた手順で作った成果物を信用しない」という機械的な扱いのほうで、
ペナルティはそのための取り決めとして置く。**

今日、黄丸241件を青丸に戻したのがこれにあたる。あれは懲罰ではなく、
「確認をサボった手順で付けた印は信用できない」という当然の処理だった。

**判定はその場で交渉しない。** 下の対応表で機械的に決める。
エージェントが「今回は軽微です」と言って軽い側に寄せるのを防ぐため、
**区分の判断に迷ったら重いほうを適用する。**

### 区分の決め方(自分で選ばない)

区分を「何が起きたか」の印象で選ぶと、必ず軽いほうに寄る。
**上から順に、はい/いいえで答えられる質問に答えて、最初に「はい」になった行の区分にする。**
報告には**質問と答えをそのまま書く。** 区分だけ書いて答えを省略しない。

| # | 質問(はい/いいえで答える) | はいなら |
|---:|---|---|
| 1 | 確かめていないことを、確かめたかのように書いたか(「未確認」を調べずに出した、件数を数えずに0と書いた、を含む) | **重** |
| 2 | 自分で作った検査に自分で合格を出して、それを完了の根拠にしたか | **重** |
| 3 | `approved:true`(赤丸)を、ユーザーの明言なしに付けたか | **重** |
| 4 | 決まっている手順を、報告せずに変えた・省いたか | **重** |
| 5 | 対になっているデータの片側だけを直したか / 再生成を忘れたか / 値を取りこぼしたか | **中** |
| 6 | 直した結果、表示される数値・判定・リンク先が変わるか | **中** |
| 7 | 上のどれでもなく、書式や見た目だけのずれか | **軽** |

- **1〜4のどれかが「はい」なら、その時点で確定。** 以降の質問は見ない。
- どの質問にも当てはまらないと思ったときは**中**にする(軽は7に該当したときだけ)。
- **重と判定したら、対応を始める前にユーザーへ報告する。** 自分で処理して完了報告に混ぜない。

### 区分ごとの対応

| 区分 | 対応 |
|---|---|
| **軽** | 直して報告。それだけ |
| **中** | ①同種を**全件横断で数えて**直す ②**監査にチェックを足す**(同じコミットで) |
| **重** | ①下の範囲で**巻き戻す** ②**自律作業を止め、1件ずつ確認に戻る** ③再開の可否はユーザーが決める |

### 巻き戻しの範囲(自分で決めない)

「そのセッションで触った該当区分」では、範囲を決めるのが巻き戻す本人になってしまう。
**gitの履歴から機械的に出す。**

起点は次の順で決める。**迷ったら古いほうを取る**(狭く取った誤りは検出できないため)。

1. 違反が混入した可能性のある最初のコミット
2. 特定できないなら、そのセッションの最初のコミットの親
3. それも分からないなら、直近でユーザーが確認した時点

```bash
python tools/rollback_reviewed.py --since <起点>          # 対象を出す(まだ書き換えない)
python tools/rollback_reviewed.py --since <起点> --apply  # 黄丸を青丸に戻す
```

対象は「起点以降に中身が変わった、または新しく増えた武将のうち黄丸のもの」。
**起点以降に触っていない武将は戻さない。触った武将は、その違反と無関係に見えても戻す。**
関係の有無を判断するのは、また本人の裁量になるため。

戻したあとは`prerender` + `gen_detail_pages`を回してからコミットする。

### 同じルールを2回破ったとき

**そのルールは「記憶では守れない」と確定したものとして扱う。**

> **監査にチェックを足すまで、その種類の作業を再開しない。**

これが一番実効性のあるペナルティ。失敗をそのまま恒久対策に変換でき、
「気をつけます」で終わらせられなくなる。チェックが書けないルールなら、
そのルール自体を層3(人が見る)へ降格させるか、廃止を提案する。

### 違反ログ

`docs/RULE-VIOLATIONS.md`に1行ずつ追記する。**消さない。**

```
| 日付 | ID | 根本原因 | 区分 | 何をしたか | 影響 | 対応 | 監査に足したか |
```

- **セッション開始時にこのログを読む。** 直近の違反と、まだ監査に落とせていない項目を把握する。
- **IDは`RULES.md`に実在するものを使う。**存在しないIDを書くと監査がHIGHで止める。
  索引に無いルールを破ったなら、先に索引へ追加してからログに書く。
- **根本原因のタグも書く。** IDが違っても、タグが同じなら2回目として数える。
  I-01とS-01はどちらも「自己承認」だったのにIDが違うため、いちばん重い扱いが発火しなかった。
  タグはログ末尾の表から選ぶ。**その場限りのタグを作らない**(毎回変えれば判定が無効になる)。
- 「監査に足したか」が空・「まだ」のまま残っている行は、監査が毎回件数を出す。
- 完了報告では、そのセッションで追記した行があれば必ず触れる。

```bash
python tools/rules.py   # 索引の件数・棚卸し日・違反ログの整合をまとめて見る
```

### 効かないと分かっているもの(やらない)

- 「以後気をつけます」と書かせる … 今日2回書いても防げていない
- マニュアルに注意書きを増やす … 破ったのは既に書いてあるルール
- 報告を長くする … 読む側の負担が増えるだけで検出力は上がらない

## ルールを新しく作るときの手順

1. **機械で判定できるか先に考える。** できるなら、ルールを書くのと同時に監査へチェックを足す。
2. **できないなら、誰がいつ確認するのかを決める。** 決まらないルールは作らない
   (守られないルールが増えると、索引全体の信頼が下がる)。
3. `RULES.md`に**IDと機械/監査の列まで埋めて**追加する。原文は各所に書いてよいが、
   索引に載っていないルールは「存在しない」ものとして扱う。

## 定期的な棚卸し

「月1回」と書くだけでは誰も呼ばないので、**監査が呼ぶ。**

`docs/RULES.md`の`最終棚卸し: YYYY-MM-DD`から31日を超えると、監査がMIDで指摘する。
併せて、索引の件数表記(「N件の索引」)が実数とずれていないかも毎回見る。
**件数のずれは、索引に手が入っていないのに現物だけ増えた合図。**

やること:

- `RULES.md`の全行を原文と突き合わせ、消えた/変わった/使われなくなったものを更新する
- 「使われていないルール」節を見直す(体制3層など、状況が変わったら復活または削除)
- 監査✗の残り件数を数え、減っているかを見る
- `python tools/rules.py`と`python tools/audit_selftest.py`を走らせ、出力を報告に貼る
- 終わったら`最終棚卸し:`の日付を更新する(これをしないと指摘が消えない)

**この棚卸し自体をサボると索引が腐り、また「ルールを認識できない」状態に戻る。**
2026-08-12の棚卸しが1回目。

## 止まる条件(競合したときの優先順位)

「ストップ」「完成まで止まらない」「1件ずつ確認」「重い違反で自律作業を止める」が
別々の場所に書かれていて、ぶつかったときどれが勝つかが決まっていなかった。
**上が勝つ。**

| 優先 | 条件 | 出典 |
|---:|---|---|
| 1 | ユーザーが「ストップ」と言った | [[feedback_work_continuation_condition]] |
| 2 | 重い違反を出した(自律作業を止め、1件ずつ確認に戻る) | 上のペナルティ |
| 3 | 短時間に確認要求が集中した(1分3回で自動全停止) | [[feedback_confirmation_flood_circuit_breaker]] |
| 4 | 新規登録フローの手順確立中(1件ずつ全工程を確認) | [[project_registration_manualization]] |
| 5 | 成果物が全て完成した | [[feedback_work_continuation_condition]] |

**「○分後に寝る」「何時に帰宅」といった時刻の話は、どれも止まる条件ではない。**
2〜4で止まっているあいだは、5(完成まで進む)を理由に再開しない。
